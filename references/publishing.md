# Publishing and public explanation

Lead with the concrete experience and the engineering discipline that makes it
credible. Show what works, what remains unknown, and how another agent can use
the skill. Avoid claims of permanent firmware, full Live2D, AI Soul, Bluetooth
transport, calibrated sensors, autonomous boot, or finished product unless exact
target evidence supports each claim.

A useful GitHub landing page contains:

1. One-sentence value proposition and a real screenshot or original diagram.
2. Current demonstrated outcomes with evidence labels.
3. A compact architecture/workflow graphic.
4. Install/invocation examples for Codex-compatible skill folders.
5. Safety boundary and excluded artifacts.
6. Repository structure and reference routing.
7. Reproducible validation command.
8. Roadmap separated from shipped capability.

Use redacted diagrams and generated previews. Do not publish serials, raw device
dumps, firmware, recovery archives, personal logs, licensed character assets or
private Soul data. Cite upstream licenses and keep test character material out
unless redistribution terms are explicitly satisfied.

For promotional wording, prefer “evidence-driven iPod nano 7G app engineering”
over unsupported permanence or AI claims. Badges may report skill validation or
host tests, but never imply a hardware gate.
